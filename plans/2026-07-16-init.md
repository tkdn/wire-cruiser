# プロジェクトの目的

Go における DI コード生成ツールである [google/wire](https://github.com/google/wire) の injector 定義(build constraint `wireinject` が付与された wire.go)を解析し、エントリポイント(injector 関数)からどのような依存を辿っているかを可視化する CLI ツールを実装する。

# スコープ外(2026-07-16 ヒアリングで決定)

- `golang.org/x/tools/go/analysis.Analyzer` API の提供、および golangci-lint へのルール組み込みは**完全にスコープアウト**する。パッケージ間依存の方向ルール検査も同様に対象外とする。
- プロバイダ関数の実装内部(通常の import 依存)までは辿らない。解析対象は wire のグラフに閉じる。
- プロバイダの cleanup 関数・error 戻り値の表示は v1 では扱わない(将来拡張)。

# 確定事項(ヒアリング結果)

1. **対象の特定**: ユーザがパスを直接指定する。自動探索モードは持たない。
   - 引数が `.go` で終わる場合はファイルパス、それ以外はパッケージパス(例: `./cmd/server`)として解釈し、両方を受け付ける。
   - パッケージパス指定時は、そのパッケージ内の `wireinject` タグ付きファイルを対象とする。
2. **解析の深さ**: `wire.Build` 直下だけでなく、別パッケージで定義された `wire.NewSet`(ProviderSet 変数)を型情報を使って**再帰的に展開**する。
3. **ノード表現**: プロバイダ関数と提供型を併記する。

   ```
   app.InitializeApp → *app.App
   ├─ app.NewApp → *app.App
   │  ├─ service.NewUserService → *service.UserService
   │  │  └─ repo.NewUserRepo → repo.UserRepo (bind: *repo.PgUserRepo)
   │  │     └─ db.NewDB → *sql.DB
   │  └─ config.Load → *config.Config
   ```

4. **出力形式**: ツリー表示(ターミナル直接出力)と Mermaid(flowchart)の 2 形式。
5. **DSL サポート範囲(v1)**: 関数プロバイダ、`wire.NewSet` に加え、`wire.Bind` / `wire.Struct` / `wire.FieldsOf` / `wire.Value` / `wire.InterfaceValue` をサポートする。
6. **不完全なグラフの扱い**: 解決できない型があってもエラー停止せず、`MISSING` 等のマークを付けてグラフに含めて出力を続行する。その場合の終了コードは非ゼロとする。壊れた wire 構成の調査用途を重視する。
7. **同一型を複数プロバイダが提供する場合**: wire ではエラーになる構成だが、警告付きで**両方表示**する。不完全なグラフと同様、調査用途を優先する。終了コードは非ゼロとする。

# CLI 仕様(確定)

```
wire-cruiser [--format tree|mermaid] <path>

  <path>     wire.go のファイルパス、または injector を含むパッケージパス
  --format   出力形式。tree (default) | mermaid
```

- 出力は stdout。injector が複数見つかった場合はすべてを順に出力する。
- injector 関数の引数(呼び出し側から与えられる値)はグラフの葉ノードとして `(arg)` 等で区別して表示する。

# 実装方針(素案)

- `golang.org/x/tools/go/packages` を用い、ビルドタグ `wireinject` を有効にした状態で対象パッケージをロードする。
- `wire.Build` 呼び出しを AST から特定し、引数を型情報(`go/types`)で解決しながらグラフを構築する。`wire.NewSet` 変数への参照は定義元パッケージを辿って再帰展開する。
- グラフ構築(コアモデル)と出力(tree / mermaid レンダラ)はパッケージを分離し、将来の JSON / DOT 出力の追加余地を残す。

# 検証事項(実装着手時に確認)

1. **wire 解析ロジックの再利用可否**: google/wire のパーサは `internal/wire` にあり外部から import できない(はず)。自前実装が前提になるが、wire 本体の最新リポジトリ構成を確認して裏取りする。
2. **バージョン確認**: 使用する Go バージョン、`golang.org/x/tools` の API(`packages.Load` のビルドタグ指定方法など)は実装着手時にリリースノート・ドキュメントで確認する。想定 module path は `github.com/tkdn/wire-cruiser`。
3. **ジェネリクスを含むプロバイダの扱い**: wire 側のジェネリクス対応状況を確認の上、v1 でサポートするか決める。
4. **Mermaid 出力の詳細**: flowchart の方向(TD/LR)、bind や MISSING のスタイル表現(点線・色分けなど)の規約。
5. **CLI フレームワーク**: 標準 `flag` で足りる想定だが、サブコマンド拡張の予定があるなら要検討。
6. **テスト戦略**: `testdata` 配下に小さな wire 使用モジュールを置き、ツリー/Mermaid 出力のゴールデンテストを行う想定。ゴールデンファイルの更新フロー(`-update` フラグ等)は実装時に決める。

# ドッグフーディング(提案)

本ツール自身の CLI 組み立て(cmd/wire-cruiser の loader / graph builder / renderer の配線)を google/wire で構成し、`wire-cruiser ./cmd/wire-cruiser` で自己可視化できる状態にする。E2E テスト兼 README のデモとして機能する。

- ただし自身のグラフは単純で、Bind / Value / MISSING などの DSL 網羅はできない。テストの主体はあくまで `testdata` のゴールデンテストとし、ドッグフーディングは従とする。
- wire の DSL 制約がツール内部設計を歪める場合(不要なインターフェース導入の強制など)は、内部設計を優先しドッグフーディングを縮小する。
